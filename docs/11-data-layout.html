01 — Topology

Two clients, one server, two different places the loop runs

exa has exactly one agent loop. The question is where that loop executes, because that single decision determines where every byte of your conversation ends up.

The critical asymmetry. A CLI session keeps its files on your machine forever and its text on your machine by default. A web chat keeps its files in an ephemeral sandbox and its text in server RAM — which means it is gone when the process restarts unless an admin opts in. Most people assume the opposite of both.

02 — Schema map

27 tables: 6 global, 20 tenant-scoped, 1 bookkeeping

The split is not cosmetic. Global tables have no row-level security and are read by the auth layer running as the table owner. Tenant tables all carry RLS and are only ever touched through withTenant(), which drops privileges to a non-owner role.

global (no RLS) tenant + partitioned encrypted at rest regular tenant table dashed = policy/credential dependency

Why messages and parts are two tables. Streaming. If the whole assistant turn lived in one messages.data JSONB blob, every token would rewrite the entire turn. Split out, a streaming update touches one small part row. blob_ref pushes large tool output out of the row entirely.

Tenancy is enforced in the database, not the app. All 20 tenant tables carry RLS and are only reachable through withTenant(), which opens a transaction, sets exa.tenant_id, and drops to the non-owner exa_app role. If a tenant id is never set, the policy resolves to tenant_id = NULL — which matches nothing. A forgotten scope returns zero rows, not every row.

05 — Storage modes

The resolver decides everything. Read this before assuming.

resolveStorageMode() in apps/server/src/routes/sessions.ts:25 is the single source of truth. First match wins.

  1. Org locked storage.modeAdmin set it with locked: true. Outranks everything, including an explicit client request.
  2. Explicit requestThe client passed --storage or the web UI asked for it.
  3. Org storage.mode settingSet but not locked.
  4. Default, by loop hostloopHost === "client" ? "local" : "none" — CLI gets local, web gets none.
  5. CoercionRequesting local on a server loop is rejected with a 400 — "storage mode local needs a client loop" — then forced to none.
  6. Org allowliststorage.allowed must contain the mode. Lock it to ["none"] and no user can ever get content on the server.

The headline. A default web chat runs in storage_mode = 'none'. Its messages and parts live in an LRU-bounded in-memory cache on the server and disappear on restart. There is a test asserting exactly this: expect(created.body.storageMode).toBe("none"). If you want web chats to persist, an admin must set storage.mode = "server".

06 — Scenarios

Two concrete journeys, step by step

A — Someone installs exa on their own laptop and uses the CLI

No cloud account. They ran bun run dev locally, or exa login --dev against their own machine, or just exa --local with no server at all. They type refactor the auth module in ~/code/my-repo.

  1. The loop starts on their laptop Not on a server. apps/cli instantiates @exa/core directly and injects local ports.
    loop_host = 'client'storage_mode = 'local'default for CLI
  2. The model call leaves the machine Either straight to the provider with their own key (local mode), or to the server gateway which holds the pool keys. Either way, the prompt text crosses the network.
    prompt → provider API
  3. The agent reads and edits files edit / bash run bash and apply_patch against ~/code/my-repo. The server never sees this.
    files stay on disk
  4. Each step is snapshotted locally A commit into ~/.exa/snapshots/<hash> — a shadow repo with its own git-dir. Your project's .git is untouched.
    ~/.exa/snapshots/
  5. The turn is appended to a local JSONL file JsonlStore writes one record per message and per part, 0600. Crash-safe: a torn last line is skipped on load.
    ~/.exa/sessions/<uuid>.jsonlNO messages/parts rows
  6. Metadata and telemetry are ingested The CLI POSTs a compact step record. The server writes a sessions row, a usage_events row (tokens, cost, model, latency), and eventually audit_log.
    sessionsusage_eventsusage_rollupsaudit_log
  7. An approval is pending (if the tool needed one) edit and non-safe bash require approval. The row is written server-side so any attached client can answer — approve from the browser, or the CLI terminal races it. First answer wins.

B — You deploy to cloud, a user signs up and chats in the browser

docker compose up behind a domain, OIDC SSO on, dev auth off. A new user opens the site, signs in with their work account, and starts a chat. The org slug comes from the OIDC tenant claim — the org is auto-created on first sign-in.

  1. The browser stores one token localStorage["exa.token"]. That's the whole client. Sign-in returns a signed JWT (typ: "web", HMAC-SHA256) carrying sub, tid, role.
    localStorage: token only
  2. The server creates the identity The ID token's signature is verified against the issuer's JWKS. A users row and a memberships row are upserted. Both are global tables — no RLS, read as owner.
    usersmemberships
  3. A session is created — and the mode defaults to none loop_host = 'server', so the resolver picks none. Messages go to an in-memory LRU cache. No messages or parts rows are written.
    sessionsmessages/parts → RAM only
  4. The loop runs on the server Same @exa/core, sandbox executor. Files live in a per-chat container: no network, read-only root, non-root, CPU/memory/pids caps. Or with no Docker configured, file tools only — no shell.
    sandbox containerephemeral

    provider_keys (envelope)decrypt → RAM → call

07 — Make it durable

How to store web chats in Postgres instead of ephemeral memory

First, a clarification. RAM is not a third storage location competing with disk and database. There are exactly two durable outcomes — none (working buffer only) or server (Postgres). none does not mean "the database was full" or "we fell back"; it means "this org has not opted into persisting content." Session metadata, token counts, cost, usage and audit are already durable in every mode — only the conversation text branches.

⚠ Side effect: this applies to CLI sessions too

resolveStorageMode() checks lockedMode and the tenant storage.mode setting before branching on loopHost — there is no per-host distinction. So setting storage.mode = "server" makes new CLI sessions store their conversation text in Postgres as well, instead of ~/.exa/sessions/*.jsonl. That is the opposite of the "CLI keeps data on your own machine" model.

ConfigurationWeb chatNew CLI sessionUser can opt out?
storage.mode="server", lockedPostgresPostgresno
storage.mode="server", unlockedPostgresPostgresyes — --storage local wins
storage.mode="local", lockedcoerced to nonelocal JSONLn/a

Recommendation for a cloud deployment: set storage.mode = "server" and leave it unlocked. Web chats persist by default; CLI developers who want their transcripts to stay on disk pass --storage local and it is honoured. Lock it only if your compliance rules demand that no conversation may exist outside the database.

Existing sessions are unaffected — storage_mode is written once into the sessions row at creation and read from there thereafter. Only new sessions pick up the new default.

How to set it — three ways

A · Web UI (easiest)

Sign in as an owner or admin → Organization settings → Chat storage → choose server → tick lock → save. Locking stops any user overriding it back.

B · API

curl -X PUT http://127.0.0.1:4317/v1/settings \
  -H "authorization: Bearer $EXA_TOKEN" \
  -H "content-type: application/json" \
  -d '{"scope":"tenant","key":"storage.mode","value":"server","locked":true}'

# optional: also lock the allowlist so nothing else is permitted
curl -X PUT http://127.0.0.1:4317/v1/settings \
  -H "authorization: Bearer $EXA_TOKEN" -H "content-type: application/json" \
  -d '{"scope":"tenant","key":"storage.allowed","value":["none","server"],"locked":true}'

scope:"tenant" requires role ∈ {owner, admin} — enforced at admin.ts:10. Every change bumps tenants.policy_version and writes an audit row.

C · Direct SQL (bootstrap / disaster recovery)

insert into settings (tenant_id, scope, scope_id, key, value, locked, updated_by)
values ('<tenant-uuid>', 'tenant', '<tenant-uuid>', 'storage.mode',
        '"server"'::jsonb, true, null)
on conflict (tenant_id, scope, scope_id, key)
do update set value = excluded.value, locked = excluded.locked;

Must run as the table owner, not exa_app — the exa_app role only has DML grants on tenant tables, and RLS won't let it see other tenants anyway.

The first two are the same database, different packaging — PGlite is Postgres compiled to WASM. "The database" and "the VM's disk" only look like different things because in dev the data directory is a plain folder on your own machine.

One caveat about the RAM cache

The LRU bound counts sessions, not bytes (maxMemorySessions = 500, sessions.ts:314). 500 large sessions could still be substantial. That's only relevant while you're on none; once you switch to server, content is only loaded when a conversation is actually opened. If you want the bound to be a true memory guarantee, a byte-based limit in ServerSessionStore would be the place to add it.

08 — Security

The five mechanisms that make this safe to host

MechanismHowWhere
RLS fail-closed Non-owner exa_app role ⇒ policies apply. nullif(current_setting(...)) means an unset tenant id matches nothing — zero rows, never all rows. db.ts:49
schema.ts:361
Transaction-scoped tenant set_config(..., true) dies with the transaction, so a pooled connection can never carry tenant A into tenant B. db.ts:20
Envelope encryption Per-secret data key encrypts the payload; the master key wraps the data key. key_version enables rotation without re-encrypting. schema.ts:145
Token hashing API tokens stored as sha256(bytes). The raw token is shown once at creation. A DB dump yields nothing usable. identity.ts:28
Locked secret floor .env, *.pem, *.key, ~/.ssh/* hard-denied in a second rule pass no session rule can outrank — even "always allow everything" can't read them. permission.ts:164
Fencing tokens Lease counter bumps on every grant. A client whose lease expired while frozen can't write on thaw — its token is stale. sessions.ts:77

One gap worth knowing. The "content only exists when storage_mode='server'" rule is application convention, not a database constraint. Nothing stops a message row being written under a local session. If you want that guaranteed, add a trigger. RLS already prevents cross-tenant reads either way.
