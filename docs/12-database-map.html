exa Database Map

Every table the exa server keeps, how they connect, and how to open the data yourself. The CLI's local chats and files live outside the database; they're listed at the end.

Production (docker compose)

The postgres service inside docker-compose.yml

docker compose exec postgres \
  psql -U exa -d exa

Not published to a host port on purpose. For a GUI, use an SSH tunnel to the host, or add a 127.0.0.1-only port mapping.

-- a few useful queries
select slug, plan, status from tenants;
select t.slug, u.email, m.role from memberships m join tenants t on t.id = m.tenant_id join users u on u.id = m.user_id;
select title, model, loop_host, storage_mode, cost_usd, updated_at from sessions order by updated_at desc limit 20;
select m.role, p.type, p.data->>'text' as text from parts p join messages m on m.id = p.message_id where p.session_id = '<id>';
select ts, action, target, decision from audit_log order by ts desc limit 50;
select model_used, sum(input_tokens + output_tokens) as tokens, sum(cost_usd) as cost from usage_events group by 1;

You connect as the database owner, so you see every organization's rows. The app itself never does: each request switches to the restricted exa_app role, and row-level security shows it only the current organization's rows.

The big picture

Four groups of tables

Everything hangs off tenants (an organization). Global tables are shared by the sign-in layer; every other table carries a tenant_id and is locked to one organization.

Group 1
GLOBAL

Identity & access

Who can sign in, and to which organization. These tables are read before the organization is known, so they sit outside row-level security. The app role can only read them.

    uuid id PK
    text email UK
    text display_name
    text auth_subject UK "OIDC subject"
  }
  memberships {
    uuid tenant_id PK,FK
    uuid user_id PK,FK
    text role "owner | admin | member | viewer"
    text status
  }
  api_tokens {
    uuid id PK
    uuid tenant_id FK
    uuid user_id FK
    bytea token_hash UK "SHA-256, never the token"
    text device_name
    timestamptz expires_at
    timestamptz revoked_at
  }
  device_codes {
    bytea device_code_hash PK
    text user_code UK "shown in the CLI"
    text status "pending | approved | denied | consumed"

TableHolds
tenantsOne row per organization. Everything else points here and is deleted with it (on delete cascade).
usersOne row per person, unique by email. A user can belong to several organizations.
membershipsUser ↔ organization with a role: owner, admin, member or viewer.
api_tokensLong-lived CLI tokens from exa login. Only a SHA-256 hash is stored, so a database leak doesn't leak tokens.
device_codesShort-lived codes for the CLI's "approve this device in your browser" login.
model_backendsRESERVEDMeant for the exa router's model pool. Today the pool comes from EXA_BACKENDS / defaults in code instead.

TENANT

TableHolds
settingsKey/value org settings (storage.mode, models.allowed, retention.contentDays, web.tools…). Defaults live in code; only overrides are stored.
permission_rulesRules like bash · git push * → ask. Locked tenant rules beat everything else.
provider_keysBring-your-own API keys, envelope-encrypted. Only the last 4 characters are readable; the server decrypts at call time with EXA_MASTER_KEY.
quotasToken, cost and request limits per day or month, for the org or one user.
skills, agent_definitionsSkills and agents published to the whole org; the CLI and web chats both load them.
projectsRESERVEDFor project-scoped settings and sessions. Columns point at it, but nothing creates projects yet.
commands, mcp_servers, secretsRESERVEDOrg-shared slash commands and server-side MCP servers. Planned; MCP still comes from local config files.
Group 3
TENANT

Sessions & conversation

One row in sessions per chat, always. The conversation text (messages and parts) is only written when the session's storage_mode is server.

    text permission_mode
    jsonb revert "pending undo point"
    bigint tokens_input
    bigint tokens_output
    numeric cost_usd
  }
  session_leases {
    uuid session_id PK,FK
    text holder_type "device | server"
    text holder_id
    bigint fencing
    timestamptz expires_at
  }
  approvals {
    uuid id PK
    uuid session_id FK
    text permission
    text_array patterns
    text state "pending | once | always | reject | expired"
    uuid decided_by
  }
  messages {
    uuid id PK
    uuid session_id FK
    uuid parent_id
    text role "user | assistant"
    jsonb data
  }
  parts {
    uuid id PK
    uuid message_id FK
    text type "text | tool | reasoning | file..."

  }
  todos {

    int position PK
    text content
    text status

TableHolds
sessionsTitle, model, agent, where the loop runs (client = CLI, server = web), storage mode, running token and cost totals. Subagent chats point at their parent.
session_leasesWhich device or server currently drives a CLI session, so two machines can't run the same chat at once.
approvals"Allow this command?" requests. Any attached client can answer; the first answer wins. They expire.
messages, partsThe conversation itself. A message is one turn; parts are its pieces (text, tool calls with output, reasoning, files). Parts are saved once per step in their final form.
todosThe agent's todo list, synced from CLI sessions. Web chats keep their todo list in server memory only.
session_eventsRESERVEDPlanned outbox so viewers on another server node can catch up. Nothing writes it yet: live events are kept in the server's memory (a short replay buffer per session). Cleanup already exists in the maintenance job.
Group 4
TENANT

Usage & audit

Append-only history, always kept regardless of storage mode. The two big tables are split into one partition per month, so old months are dropped whole instead of deleted row by row.

  tenants ||..o{ usage_rollups : ""
  tenants ||..o{ audit_log : ""
  sessions |o..o{ usage_events : "session_id"
  usage_events }o..|| usage_rollups : "summed into"
  usage_events {
    uuid id PK
    timestamptz ts PK "partition key"
    uuid user_id
    uuid session_id
    text model_requested "e.g. exa"
    text model_used "the real model"
    text key_source "user | tenant | pool"
    int input_tokens
    int output_tokens
    numeric cost_usd
    int latency_ms
    text status
  }
  usage_rollups {
    text subject_scope PK
    uuid subject_id PK
    text period PK "day | month"
    date period_start PK
    bigint tokens
    numeric cost_usd
    int requests
  }
  audit_log {
    uuid id PK
    timestamptz ts PK "partition key"
    uuid actor_user_id
    text device
    uuid session_id
    text action "login, session.created, tool..."
    text target
    text decision
    jsonb meta
  }
TableHolds
usage_eventsOne row per model call: which model was asked for vs. used, whose key paid, tokens, cost, latency. Physical tables: usage_events_202610, _202611… plus _default.
usage_rollupsRunning daily and monthly totals per org and per user. Quota checks read these instead of summing raw events.
audit_logWho did what: sign-ins, tokens, settings and key changes, sessions, tool runs and permission decisions. Same monthly partitions.

Rules the schema follows

One organization per query

Every tenant table has a row-level security policy on tenant_id. The app sets exa.tenant_id and switches to exa_app inside each transaction, so even a buggy query can't see another org.

Chat text is optional

none: kept in memory only. local: on the user's Mac. server: in messages/parts. Admins can lock the mode for the org.

Secrets are never readable

API tokens are hashed. Provider keys and secrets are AES-256-GCM encrypted with a per-secret key, wrapped by a versioned master key that never touches the database.

Time-ordered ids

Ids are UUIDv7, so they sort by creation time and keep indexes compact.

Some links are ids, not foreign keys

High-volume and partitioned tables (usage, audit, events) skip foreign keys to keep inserts cheap and history intact after deletes.

Migrations run on startup

Plain SQL in packages/store/src/migrations/schema.migrations.ts, recorded in exa_migrations. Two so far: 001_init and 002_partition_fn.

How long data stays

Chat content30 days by default for server mode (org setting retention.contentDays), then deleted by the maintenance job.
Usage & audit13 months (EXA_USAGE_RETENTION_MONTHS). Older monthly partitions are dropped.
Live eventsServer memory only, a short replay buffer per session for reconnecting viewers.
Approvals, device codesExpire after their expires_at.
Session metadataKept until the user forgets the session or the org is deleted.
